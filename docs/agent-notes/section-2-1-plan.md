3. Распределить данные между связанными текстовыми и бинарными файлами; обосновать назначение каждого файла. Не увеличивать число файлов искусственно.

6. Выбрать собственные контейнеры и средства STL для работы с данными в памяти.
7. Описать входные данные и результаты, которые выдаёт программа пользователю.
8. Подготовить таблицы структуры файлов и схему связей; после согласования написать раздел 2.1.

## Согласованные решения

### Пользователи

- У каждой учётной записи ровно одна роль: покупатель, продавец или администратор. Продавец не может одновременно выступать покупателем.
- Поля: идентификатор, логин, пароль, отображаемое имя, роль, телефон и адрес.
- Из телефона и электронной почты выбран телефон; почту пока не хранить.
- Пароль хранится в виде хеша, поле хеша имеет тип `string` (согласовано студентом). Алгоритм хеширования и структура адреса ещё не выбраны.

### Категории и свойства

- Категории образуют дерево; категория имеет родительскую категорию, кроме корневых.
- Подкатегория наследует свойства родительской категории и её предков и добавляет собственные.
- Категории и наборы свойств создаются администратором во время работы, без изменения и перекомпиляции кода.
- Свойство имеет название, тип и признак обязательности. Типы: текст, целое число, дробное число, да/нет.
- При создании категории можно определить обязательные и необязательные свойства.
- После создания категории разрешено добавлять только необязательные свойства. Это также важно для товаров в существующих подкатегориях.
- Изменение типа, удаление свойства и изменение его обязательности пока не согласованы.

### Товары

- Каждый товар относится к одной категории и одному продавцу. Один товар не имеет нескольких продавцов.
- Поля: идентификатор, название, описание, цена, категория, продавец, количество товара, бренд и значения свойств категории.
- Помимо собственных свойств категории учитываются унаследованные свойства.
- Отсутствующее необязательное значение нужно отличать от пустого текста, числа 0 и значения «нет»; способ представления выбрать при проектировании формата.
- Оценки хранить отдельными записями, связанными с товаром и покупателем; среднюю оценку вычислять по ним.
- Фотографии пока не реализовывать. Сохранить эту идею для возможного добавления в конце проекта.

### Заказы

- В одном заказе может быть несколько товаров разных продавцов.
- Каждый продавец подтверждает только свою часть заказа. Подтверждённая часть считается отправленной; реальная доставка не моделируется.
- Части одного заказа могут находиться в разных состояниях.
- Рабочая модель: общий заказ и его позиции; для подтверждения нужно различать части по продавцам. Нужны ли для этих частей отдельные записи, решить при проектировании файлов.
- Предложено сохранять количество и цену на момент покупки в позиции заказа, а адрес доставки — в самом заказе. Эти детали были предложены в обсуждении и требуют окончательного согласования; текущие цена товара и адрес профиля не должны определять историю заказа.

### Оценки и отзывы

- Оценка от 1 до 5; текст отзыва необязательный.
- Оценки и отзывы доступны после оформления заказа на соответствующий товар.
- Рабочая трактовка ответа «пускай так»: один покупатель оставляет один отзыв на товар и может его редактировать. Повторная покупка не создаёт второй отзыв. Перед фиксацией формата уточнить эту трактовку.
- Продавец может отвечать на отзывы о своих товарах. Количество ответов и возможность их редактирования ещё не согласованы.

### Удаление товаров

- Пользователь допустил сохранение товара для истории заказов, но просит не усложнять структуру.
- Простое предлагаемое решение: поле активности в записи товара. При удалении товар скрывается из каталога, а запись и идентификатор сохраняются для связей с заказами и отзывами. Отдельный архивный файл не нужен.
- Это предложение по реализации, а не утверждённый формат. Физическое удаление, восстановление товара и отображение скрытого товара в старых заказах ещё не определены.

## Что учитывать при дальнейшем проектировании

- Нужна функциональная иерархия классов с не менее чем тремя уровнями наследования. Не вводить уровни только ради выполнения требования.
- Дерево категорий и наследование классов C++ — разные вещи. Категории должны оставаться данными: не создавать отдельный класс для каждой пользовательской категории.
- Будущую иерархию строить вокруг различий в поведении объектов; конкретные классы согласовать позднее.
- Учитывать возможное расширение данных и добавление свойств. Пока только отметить эту потребность, не разрабатывать общий механизм миграций и версионирования.
- По заданию нужны собственные контейнеры, итераторы и алгоритмы наряду со средствами STL, обработка исключений и отмена последних изменений.
- Ранее зафиксирована одновременная работа нескольких экземпляров с общими файлами; порядок согласования изменений ещё не выбран.
